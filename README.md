# samat-3d

خط لوله‌ی ساخت خودکار مدل سه‌بعدی از عکس‌های پهباد برای اپ SAMAT، با OpenDroneMap روی GitHub Actions.

**این ریپو عمومی است. همه‌ی عکس‌ها و مدل‌ها فقط به‌صورت رمزشده (AES-256-GCM) اینجا قرار می‌گیرند.**

## جریان کار

1. اپ برای هر پروژه یک `job_id` تصادفی (۱۶ تا ۳۲ کاراکتر hex) و یک کلید ۲۵۶ بیتی تصادفی می‌سازد. کلید فقط در Supabase نگهداری می‌شود.
2. عکس‌ها در مرورگر رمز می‌شوند و به‌صورت asset‌های `NNNN.enc` در Release با تگ `in-<job_id>` آپلود می‌شوند (از طریق Edge Function، نه با توکن داخل اپ).
3. Edge Function ورک‌فلوی `build-3d.yml` را با ورودی `job_id` اجرا می‌کند.
4. ورک‌فلو کلید را از Edge Function می‌گیرد، عکس‌ها را رمزگشایی می‌کند، ODM را اجرا می‌کند و `model.glb` را رمز کرده در Release با تگ `model-<job_id>` می‌گذارد.
5. عکس‌های خام (Release `in-...`) حذف می‌شوند و نتیجه به اپ اطلاع داده می‌شود.
6. اپ هر وقت لازم شد `model.glb.enc` را می‌گیرد، در مرورگر رمزگشایی می‌کند و نشان می‌دهد. در Supabase فقط یک ردیف کوچک (وضعیت و تگ) می‌ماند.

## Secrets لازم (Settings > Secrets and variables > Actions)

| نام | کاربرد |
|---|---|
| `KEY_URL` | آدرس Edge Function که کلید را می‌دهد |
| `KEY_TOKEN` | توکن احراز هویت آن Edge Function |
| `CALLBACK_URL` | آدرس Edge Function که نتیجه را می‌گیرد (اختیاری) |
| `CALLBACK_TOKEN` | توکن آن (اختیاری) |
| `TEST_KEY_B64` | فقط برای تست دستی، وقتی `KEY_URL` تنظیم نشده |

قرارداد `KEY_URL`: درخواست `POST {"job_id": "..."}` با هدر `Authorization: Bearer <KEY_TOKEN>` و پاسخ `{"key_b64": "..."}`. Edge Function فقط برای `job_id`هایی که واقعاً در Supabase ثبت شده‌اند کلید بدهد.

ورودی‌ها و لاگ‌های اجرا در ریپوی عمومی برای همه دیدنی است. کلید هرگز نباید ورودی ورک‌فلو باشد.

## فرمت رمزنگاری (S3D1)

توضیح کامل در سربرگ `scripts/s3d.py`. خلاصه: هدر ۱۶ بایتی (`S3D1` + پیشوند nonce هشت‌بایتی + اندازه‌ی chunk)، سپس chunk‌های ۴ مگابایتی AES-GCM. nonce هر chunk برابر پیشوند به‌اضافه‌ی شماره‌ی chunk است و AAD شامل شماره‌ی chunk و پرچم «آخرین chunk» است. این فرمت با WebCrypto مرورگر سازگار است.

## تست دستی

```bash
export S3D_KEY_B64=$(python scripts/s3d.py keygen)
JOB=$(openssl rand -hex 8)
python scripts/s3d.py encrypt-dir ./photos ./enc
gh release create in-$JOB ./enc/*.enc --repo samtqorve-lab/samat-3d --title in-$JOB --notes test
gh secret set TEST_KEY_B64 --body "$S3D_KEY_B64" --repo samtqorve-lab/samat-3d
gh workflow run build-3d.yml --repo samtqorve-lab/samat-3d -f job_id=$JOB
```

برای دیدن مدل: `model.glb.enc` را از Release `model-$JOB` بگیرید و با `python scripts/s3d.py decrypt model.glb.enc model.glb` باز کنید.

## ادغام چند پرواز برای معدن‌های بزرگ (`merge-3d.yml`)

معدن‌های بزرگ معمولاً با یک پرواز پوشش داده نمی‌شوند. راه‌حل: هر پرواز مثل قبل جداگانه با `build-3d.yml` پردازش می‌شود (هر کدام `job_id` و کلید خودش را دارد)، و بعد ورک‌فلوی جدید `merge-3d.yml` نتایج چند پرواز کامل‌شده را در یک پوشش واحد ادغام می‌کند.

**پیش‌نیاز هر پرواز شرکت‌کننده در ادغام:**
- باید با `"mode": "survey"` پردازش شده باشد (تا `dsm.tif` تولید شود؛ حالت `preview` قابل ادغام نیست).
- باید دارای مختصات جغرافیایی واقعی باشد — یعنی عکس‌ها EXIF/GPS داشته باشند (`georef: "exif"` کافی است) یا بهتر، `geo.txt`/`gcp_list.txt`. برای معادن بزرگ که چند پرواز باید دقیق روی هم بیفتند، `georef: "gcp"` با نقاط کنترل مشترک بین پروازها دقت به‌مراتب بهتری می‌دهد.
- تعیین صریح `crs` (مثلاً `"EPSG:32638"`) در `job.json` هر پرواز توصیه می‌شود تا مطمئن شوید همه‌ی پروازهای یک معدن روی یک سیستم مختصات‌اند؛ در غیر این صورت `merge-3d.yml` خودش پروازها را (با gdalwarp) به سیستم مختصات اولین پرواز تبدیل می‌کند.

**چه چیزی ادغام می‌شود:**
- `dsm.tif` (مدل ارتفاعی یکپارچه) همیشه.
- `ortho.tif` (ارتوفتوی یکپارچه) فقط اگر همه‌ی پروازهای شرکت‌کننده ارتوفتو داشته باشند.
- `model.glb` — یک **مش سه‌بعدی بافت‌دار برای کل معدن**، ساخته‌شده توسط `scripts/build_mesh_from_raster.py` مستقیماً از روی همان `dsm.tif`/`ortho.tif` یکپارچه (یک مش گرید/heightmap، نه بازسازی مجدد فتوگرامتری با ادغام ابرنقاط چند پرواز — آن کار به تراز کردن با ICP و re-mesh نیاز دارد که در این نسخه پیاده نشده). این مش برای دیدن کل معدن (پله‌ها و جاده‌های دسترسی) در یک نما کافی است؛ برای جزئیات نزدیک هر پرواز، همان `model.glb` تک‌پروازی از `build-3d.yml` دقت بیشتری دارد و همچنان در دسترس می‌ماند.
  می‌توانید با ورودی `build_mesh: false` این مرحله را رد کنید و فقط رستر یکپارچه (dsm/ortho) را بگیرید.

هر سه در همان Release با تگ `model-<merge_job_id>` قرار می‌گیرند — دقیقاً مثل خروجی یک پرواز عادی (`model.glb.enc`, `dsm.tif.enc`, `ortho.tif.enc`)، پس اپ می‌تواند همان مسیر دانلود/رمزگشایی/نمایش موجود (`model3dViewer.js`) را برایش استفاده کند بدون هیچ تغییری.

**نحوه‌ی اجرا** (اپ باید مثل یک `job_id` معمولی، یک `merge_job_id` جدید در Supabase ثبت کند تا `KEY_URL`/`CALLBACK_URL` برایش هم کار کنند — این بخش سمت Supabase/Edge Function است و در این ریپو نیست):

```bash
gh workflow run merge-3d.yml --repo samtqorve-lab/samat-3d \
  -f job_ids="jobid1111111111 jobid2222222222 jobid3333333333" \
  -f merge_job_id="newmergejobid123" \
  -f crs="EPSG:32638"
```

**محدودیت‌های شناخته‌شده (صادقانه، نه پنهان‌شده):**
- ادغام DSM/ارتوفتو یک mosaic ساده است (روی هم‌پوشانی‌ها آخرین پیکسل برنده است)، بدون seamline/رنگ‌آمیزی یکنواخت بین پروازها — برای محاسبات حجمی و نمایش زمین کافی است، اما ممکن است در ارتوفتوی نهایی خط درز بین پروازها دیده شود؛ همین خط‌درز روی بافت مش سه‌بعدی هم منتقل می‌شود.
- مش سه‌بعدی کل معدن یک heightmap با وضوح محدود است (پیش‌فرض حداکثر ۴۰۰×۴۰۰ رأس ≈ تا ۳۲۰ هزار مثلث) — ریزجزئیات کمتر از مش فتوگرامتریک بومی هر پرواز دارد.
- محور «بالا» در این glb هم مثل خروجی خودِ ODM روی Z است (نه قرارداد Y-up خودِ glTF)؛ همان تشخیص خودکار که در `model3dViewer.js` برای مدل تک‌پروازی هست، برای این مدل هم کار می‌کند، پس چیزی در اپ عوض نمی‌شود.

## نکات

- عکس‌ها باید **EXIF/GPS** داشته باشند. ODM از آن برای مقیاس و سرعت تطبیق استفاده می‌کند. اگر اپ عکس را کوچک می‌کند، باید EXIF را حفظ کند.
- تنظیمات پیش‌فرض ODM سبک هستند (کیفیت پایین، بدون ارتوموزاییک). با ورودی `odm_options` قابل تغییرند.
- Failed jobها عکس‌ها را نگه می‌دارند تا بشود دوباره اجرا کرد، و `cleanup-stale-photos` بعد از ۲ روز آن‌ها را پاک می‌کند.
- اگر دانلود مستقیم Release از مرورگر به‌خاطر CORS مسدود شد، دانلود مدل از طریق Edge Function پراکسی می‌شود.
